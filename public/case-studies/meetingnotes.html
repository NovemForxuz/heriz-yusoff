What this case study is actually showing

MeetingNotes records a Discord meeting and turns it into structured notes — automatically. Solo project, built end-to-end by me over three days, paired with Claude Code for implementation — I made every design call and verified every claim below myself against a real recording; nothing here is an AI-generated summary of work I didn't drive.

Debugs from evidence

The documented API 404'd, so I found the real one by reading a live JS bundle and verified it byte-for-byte.

 Designs for failure boundaries

Isolated the bot from pipeline crashes with a subprocess boundary — one bad meeting can't take down the next one.

 Ships, then hardens under real use

 Names tradeoffs instead of hiding them

DAY 1 · 18 AUG

The MVP, and where the base model falls apart

base model mangles domain jargon

0ba32d0

The default Whisper model was tested against a real recording full of this project's own vocabulary — and lost the vocabulary. Toggle below to hear the difference a model size made.

Confirmed in testing Language auto-detect misfired on the same file too, locking onto ms (Malay) for English audio — it only samples the first ~30s. Best result: --model small + --language en + --initial-prompt primed with the project's own terms.

torch silently picks CPU over a real GPU

0ba32d0

A GTX 1650 Ti was present, but torch.cuda.is_available() returned False — plain pip install torch installs the CPU-only build on Windows by default. Measured afterward, on CPU, against a real ~105s clip:

Measured, not estimated base auto-detect: ~18–20s · small + lang + prompt: ~32s — roughly 2× slower, extrapolating to ~9–10 min for a real 30-minute meeting on this machine's CPU.

Auto-pick from input/, timestamp every output

4b01daa

Drop a file in input/ and omit the path — errors loudly instead of guessing if zero or several files are there. Every output gets a timestamp prefix so repeat runs never silently overwrite each other.

DAY 2 · 19 AUG

Grounding the model in things it can't guess

--notes-file: your own notes outrank the transcript

cebece5

A raw transcript is often ambiguous even to a careful human reader. The fix: let the user's own rough notes act as ground truth, authoritative over the transcript when the two disagree.

Confirmed in testing Adding a short notes file surfaced an action-item owner with zero recognizable mention anywhere in the Whisper transcript, and recovered several items a transcript-only run had missed.

Speaker diarization, solved by not guessing

a649170

Whisper has no concept of who's talking on a mixed-down recording. Craig records each speaker to a separate track — so each track is transcribed independently, then merged chronologically. Attribution by construction, not inference.

Confirmed in testing Most of any one track is silence. Built-in no_speech_prob alone missed background noise that produced fabricated text — measured avg_logprob ≈ −4.8 on real garbage output vs. −0.6 to −0.9 for genuine speech. Now filters on both.

Verify the name-map once, then reuse it

078c690

Discord usernames get relabeled to real names before summarization, not left for the model to resolve mid-sentence.

Confirmed in testing Whisper consistently misheard "Heriz" as "Harris" throughout a real transcript. Relabeling first measurably improved attribution over passing --participants alone.
DAY 3 · 20 AUG

From script to system

Three passes to stop content going missing

8afdb22

Summarizing a long transcript in one pass compresses — quietly dropping minor-seeming details. The fix restructures one call into three.

Mechanism

How the verify pass catches what organize drops

On a real ~30-minute, 5-person transcript, the organize pass alone dropped a decision and an action item that were both cleanly present in the extract pass — despite explicit "never drop a bullet" instructions. The verify pass diffs against the raw extraction and backfills what's missing.

Caveat found in the same test Verify fixed the dropped content completely — but occasionally misattributed who said a backfilled line when it landed near a speaker transition. Content loss: solved. Per-line attribution: not yet perfect. --single-pass skips all three steps and trades that completeness back for speed — confirmed to drop real content on long transcripts, so reserved for low-stakes runs only.

The API scaffold gets dropped, not kept "just in case"

739a12b

The ASP.NET scaffold from the very first commit had never been wired to anything. With the pipeline confirmed Python end to end, an HTTP layer between it and the Discord bot was never actually needed — so it was removed rather than carried forward.

Read the source, then verify against the real thing

0404ed8 · ea497cb

Craig has no public bot API. The first version of craig_client.py was reconstructed by reading Craig's public GitHub source. It was wrong.

An error message that was too honest to send

ea497cb

Error messages embedded Craig's raw API response with no length limit. On the failing request, that response was itself long enough to exceed Discord's 4000-character message limit — so the bot's attempt to report the real error failed too, masked behind Discord's own length-limit error instead of the actual cause. Fixed with truncation at both the source and the point of use.

Shelling out on purpose

0404ed8

The Discord bot calls pipeline.py as a separate subprocess rather than importing its functions directly — because the pipeline scripts call sys.exit() on error by design, correct for a one-shot CLI script, wrong for a long-running bot.

Trading seconds for a cleaner filename

b355502

Output timestamps dropped from HHMMSS to HHMM. The resulting same-minute collision case — two runs in the same minute now overwrite each other — was accepted and written down as a known, low-likelihood tradeoff rather than hedged against.

Shipped it, then immediately used it for real

The bot went live around midnight — and real use found four more bugs within the hour, each one a config gap or a UX shortcut rather than a broken feature.

DAY 3 (LATE) · 20–21 AUG

One real run, one real speaker shown as two people

acc9545

Diagnosed from an actual bot run: without CRAIG_NAME_MAP set, the transcript kept raw Discord usernames, and the summarizer split one real speaker into two identities in the notes.

Real bug, real run "Madooshik95" and "Aaron" appeared as two separate people in the Discussion section — same person, confirmed against transcript content weeks earlier. Fix: run_pipeline() now also derives --participants from CRAIG_NAME_MAP's real-name side automatically — relabeling alone wasn't the full fix; all three grounding levers (relabeled transcript + --participants + --notes-file) together were what testing had already shown worked best.

Notes that aren't the same file every time

bba1201

A static MEETING_NOTES_FILE path meant editing .env and restarting the bot before every meeting with different rough notes. /meetingnotes now takes an optional attachment instead — per-meeting notes, when given, override the static default; omitting it falls back unchanged.

"I don't see the new option" — an hour-long red herring

b117ae2

The new notes-attachment parameter was real and correctly registered — just not visible yet.

Root cause tree.sync() with no guild registers commands globally, which Discord can take up to an hour to propagate. Added an optional DISCORD_GUILD_ID for guild-scoped registration, which syncs instantly — with a printed warning if left unset, rather than silently eating the delay.

A progress bar driven by real signals, not a spinner

5970535

Sitting through a silent multi-minute wait made the next fix obvious: surface what's actually happening, from data the system already has.

Confirmed in testing estimate_cook_progress() reads Craig's real job-status transitions (starting → encoding → finalizing → complete, with real per-track percentages); the bot separately parses pipeline.py's actual stdout ("Transcribing track X/Y", "Pass X/3"), weighted 90/10 transcription/ summarization to match real observed timing — transcription dominates wall-clock time. One Discord message is edited in place, throttled against rate limits, instead of spamming new ones per update.
Reflection

What I'd tell someone reading the commits

No decision above was made in the abstract — each one starts from a specific failure on a specific recording, and I judged the fix only by whether a re-run actually closed it. Three things I noticed about my own process, looking back:

Evidence over intuition

"base should be fine" and "the repo says /api/recording/:id" both sounded reasonable to me and were both wrong until I tested against a real file and a real request. I'd rather be slow and right than fast and plausible.

Ground truth over inference

Per-speaker tracks instead of diarization guesswork; a human's own notes outranking the transcript when they conflict — I kept reaching for a known fact before a smarter guess, and it paid off every time.

Tradeoffs named, not hidden

Three-pass summarization costs 3× the API calls. Multitrack costs N× the runtime. I wrote every one of these down as a conscious choice rather than let a shortcut hide as a default.

If I rebuilt this today, I'd add the diarization filtering thresholds as config instead of constants the first time, not the second — I ended up hand-tuning avg_logprob against one real recording, which works, but won't generalize to a noisier room without someone re-tuning it by hand again.

Status

Where it stands, 21 Aug 2026

  1. The full loop is not just built but dogfooded — real /meetingnotes runs through Discord's own interaction flow found and fixed four real bugs the same night it shipped (duplicate speakers, static notes, an invisible new option, a silent multi-minute wait).
  2. Every bug found so far has been a config/UX gap, not a broken core mechanism — the transcription and summarization pipeline underneath has held up across all of it.
  3. Multi-speaker overlap on a single mixed-down file is still unsolved — out of scope for this MVP, would need a dedicated diarization step.
